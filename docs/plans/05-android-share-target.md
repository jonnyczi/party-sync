**Order:** Independent of Plans 1–4, sequenced last. Benefits from Plan 1's
concurrency for multi-file shares, so ideally build after Plan 1 is merged. This

## Context / why

The app only uploads via scheduled/manual **jobs**. There's no way to ad-hoc push
"this photo / these files" to a server from another app. An Android **share
target** makes the app a first-class destination in the system share sheet — a
very natural capability for a copyparty client.

## Locked decision

- Handle **SEND and SEND_MULTIPLE**, any mime type. On receive, show a **server +
  remote-folder picker**, then do a **one-off upload** (no persisted job).
  Whether to log it to run history is an open question (see below).

## Key files / what changes

- **`app.json`** — add `expo.android.intentFilters` entries for
  `android.intent.action.SEND` and `android.intent.action.SEND_MULTIPLE` with
  appropriate `mimeType`(s) so the app appears in the share sheet. (Must go
  through `app.json` — `android/` is regenerated by `expo prebuild`.)
- **Receiving the shared payload — the main risk.** `expo-linking` only surfaces
  the intent **data** URI, not the `EXTRA_STREAM` / `ClipData` content URIs that
  SEND/SEND_MULTIPLE carry. Plan to read those **natively**: extend the existing
  `modules/copyparty-sha512` Expo module (or add a small sibling module) to expose
  the shared `content://` URIs to JS on launch/resume (read
  `Intent.EXTRA_STREAM` / `intent.clipData`). That module already opens
  `content://` URIs for `size` / `readRange` / `hashFileChunks`, so the uploader
  can consume the shared URIs **with no extra storage permission**.
- **New route `app/share.tsx`** — entered when the app is opened via a share
  intent. It: receives the URI list; lets the user pick a **server** (reuse the
  server-list UI pattern from `app/job/[id].tsx`) and a **remote folder** via the
  existing `RemotePathBrowser` (`components/remote-path-browser.tsx`); shows
  upload progress; and uploads each URI with `uploadFile`
  (`src/copyparty/up2k.ts`) against a `CopypartyClient`
  (`src/copyparty/client.ts`).
- Use `nativeFileSource` (`src/copyparty/hash.native.ts`) for size/hash/read of
  the shared content URIs, and `getServerPassword` (`src/storage/secrets.ts`) for
  auth. Optionally reuse `dateSubdir` (`src/sync/path-organization.ts`) if the
  user wants organized output.

## Reuse

`RemotePathBrowser`, `CopypartyClient`, `uploadFile`, `nativeFileSource`,
`getServerPassword`, and the server-selection UI from `app/job/[id].tsx`. If you
want live progress, consider a local progress model or reuse the `ProgressBus`
shape — but note one-off shares aren't tied to a `jobs` row.

## Open questions for this session

1. **Native intent handling** (decide with the user): extend
   `modules/copyparty-sha512`, add a new small native module, or adopt a community
   lib. Any lib **must stay non-Google** for F-Droid — e.g. `expo-share-intent`
   would need to pass `scripts/scan-nonfree-apk.py`. Recommend extending the
   existing module to avoid a new dependency.
2. **Log one-off uploads to history?** `runs.job_id` is `NOT NULL REFERENCES
   jobs(id)`, so logging needs either a pseudo "share" job or a schema relaxation.
   Simplest v1: **don't** log — show in-screen progress only. Confirm.
3. **Date organization** — reuse a chosen server's date bucketing for shared
   files, or drop them flat into the picked folder?
4. **Default remote folder** — remember the last-used folder per server, or always
   start at root?
5. **Duplicate-name handling** — copyparty may rename on collision (the up2k
   handshake returns the final name); surface the final name(s) to the user?

## Verification

- **Emulator:** share photos from the Gallery (single → SEND; multiple →
  SEND_MULTIPLE) → the app appears in the share sheet → pick server + folder →
  files upload. Verify server-side with `curl -u test:testpw ".../?ls=..."`.
- **Non-free gate / release build:** build a **release** APK
  (`dagger call build-apk export --path ./out/app.apk`) and run
  `scripts/scan-nonfree-apk.py` to confirm the share handling added no non-free
  deps. (Release builds also exercise the real manifest the intent filters land
  in.)
