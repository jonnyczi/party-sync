## Context / why

Today the engine uploads files **strictly one at a time** with one chunk per POST
(`src/sync/engine.ts` does `for await … of walker.walk()` and awaits each
`uploadFile`; `src/copyparty/up2k.ts` posts a single chunk per request). For a
multi-thousand-photo camera-roll backup over Wi-Fi this leaves most of the uplink
idle and is the single biggest perceived-speed problem. The progress UI also only
shows the current file's percentage — there's no overall "how much is left",
and the dedup savings that up2k already computes are discarded.

## Goal

Parallel, observable uploads: **per-job file concurrency**, **chunk stitching**
within a file, an **exact overall progress bar + ETA**, and a **"saved via dedup"
stat**.

## Locked decisions

- Concurrency is **per-job**: add `jobs.max_concurrency INTEGER NOT NULL DEFAULT 3`
  (migration v4), with a control in the job editor.
- Progress uses an **exact pre-scan pass**: drain the walker into an array first
  (exact `totalFiles` + `totalBytes`), then upload from the array with a
  concurrency pool. Entries are tiny (uri, path, size, mtime) so even a
  50k-asset camera roll is fine in memory.
- Dedup savings are recorded per run: add `runs.bytes_deduped INTEGER NOT NULL
  DEFAULT 0` (same migration).

## Key files / what changes

- **`src/copyparty/up2k.ts`** — chunk stitching. Batch contiguous missing chunks
  into one `client.uploadChunk` call: copyparty accepts comma-joined hashes in
  `X-Up2k-Hash`, and `client.uploadChunk` already accepts a `subc` field (→
  `X-Up2k-Subc` header). Cap the stitched payload (≤ a few MiB or N chunks) so the
  RN `fetch` body stays reasonable. Return per-file `dedupSavedBytes` on
  `UploadResult` (`= size - bytesUploaded`; full `size` when `alreadyExisted`).
  Note: `UploadOptions.precomputedHashes` already exists — leave the hashing path
  as-is unless you also persist hashes (out of scope here).
- **`src/sync/engine.ts`** — rework `runJob`:
  - **Scan phase:** drain `walker.walk(job.source_uri)` into an array, computing
    exact `totalFiles` and `totalBytes`; emit them to the progress bus before
    uploads begin.
  - **Upload phase:** a **concurrency pool** of size `job.max_concurrency` running
    `uploadFile` for up to N files at once. **Keep** the `withRetry` wrapper, the
    `(size, mtime)` skip short-circuit against `file_state`, per-file
    error→`run_errors` recording (run continues), and the 401/403 "fatal for run"
    rule (`isFatalForRun`) — on a fatal error, stop scheduling new files and let
    in-flight ones settle.
  - Accumulate `bytesUploaded` **and** `bytesDeduped`; pass `bytes_deduped` to
    `runsDao.finishRun`. `upsertFileState` rows are keyed by `(job_id,
    local_path)` so concurrent writes are already independent.
- **`src/sync/progress.ts`** — extend `ActiveRunSnapshot`: add run-level
  `totalFiles`, `totalBytes`, `uploadedBytes` (+ keep `startedAt` for ETA), and
  **replace the single `activeFile`** with `activeFiles: ActiveFileSnapshot[]`
  keyed by `localPath`. Add mutators `setTotals(...)`, `startFile(file)`,
  `updateFileBytes(localPath, bytes)`, `endFile(localPath)`. Keep every mutation
  immutable (fresh top-level object) so `useSyncExternalStore` re-renders.
- **`src/db/schema.ts`** — migration v4 (the two columns above). Follow the
  existing `MIGRATIONS` array + `schema_migrations` pattern.
- **`src/db/types.ts` / `src/db/jobs.ts` / `src/db/runs.ts`** — thread
  `max_concurrency` and `bytes_deduped` through row types, create/update inputs,
  and `finishRun`.
- **`app/job/[id].tsx`** — add a concurrency field to the job form (stepper or
  number input), clamped to a sane range (suggest 1–8). Update `ActiveRunPanel`
  to show the overall bar (`uploadedBytes/totalBytes`), an ETA, and a short list
  of in-flight files (instead of a single file).
- **`app/(tabs)/index.tsx`** — `ActiveRunCard`: overall progress + ETA; add a
  "saved X via dedup" line when `bytes_deduped > 0`.
- **`app/run/[id].tsx`** — add a "Deduplicated" stat to the stats grid (reads
  `run.bytes_deduped`).
- **`hooks/use-sync-progress.ts`** — likely no API change; verify it reflects the
  reshaped snapshot and screens consuming `activeFile` are updated to
  `activeFiles`.

(in `engine.ts`), `defaultProgressBus` (`src/sync/progress.ts`), the

## Open questions for this session

1. Default `max_concurrency` and allowed range (suggest default **3**, range 1–8).
2. Should concurrency **auto-clamp on cellular** (e.g. force 1–2), or always
   honor the per-job value?
3. Max **stitched-chunk payload size** before splitting a POST (memory vs request
   count trade-off).
4. **ETA smoothing** — instantaneous rate vs a moving average — to avoid a jumpy
   estimate, especially early in a run.
5. Per-file progress under concurrency can interleave — confirm the
   `activeFiles[]` UI (list vs just an aggregate bar) the user wants.
