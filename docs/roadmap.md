## 1a. (original notes) Cleartext-HTTP blocked in release builds

**Symptom.** A **release** APK can't talk to plain `http://` copyparty servers:
every request fails with **"Network request failed"** (e.g. "5 scanned, 0
uploaded, 5 failed"). Debug/dev builds work, because Expo/RN dev builds set
`usesCleartextTraffic=true` — so this only bites the *published* flavor (GitHub
Releases, F-Droid, Play). Many copyparty deployments are plain `http://` on a LAN,
so real users will hit this. Discovered 2026-06-28 while smoke-testing on the
emulator against the dockerized copyparty at `http://10.0.2.2:3923`.

**Why it's not yet fixed.** It needs a product decision (how permissive to be) —
not just code. Pick one with the user:
- Broadest/simplest: `expo.android.usesCleartextTraffic: true` in `app.json`
  (re-enables cleartext app-wide; least safe).
- Safer: a custom `network_security_config.xml` injected via a config plugin
  (mirror `plugins/withReleaseSigning.js`) — allow cleartext only for user-added
  hosts, or default-allow with a per-server opt-in.
- Or push users to `https://` (copyparty supports TLS) and surface a clear in-app
  error when a cleartext request is blocked.

**Key constraint.** `android/` is gitignored and regenerated by `expo prebuild`,
so the manifest/network-config change **must** flow through `app.json` or an Expo
config plugin — never hand-edit `AndroidManifest.xml`.

**How to verify a fix.** Build a **release** APK (`dagger call build-apk`), install
it, and retry a sync against an `http://` server (the dockerized copyparty at
`http://10.0.2.2:3923` from the emulator). The upload should succeed instead of
"Network request failed".

## 2. F-Droid submission 🟡 (recipe drafted, blocked on prerequisites)

The de-Googling is done (zero Firebase/GMS — guarded by `scripts/scan-nonfree-apk.py`
in CI) and the recipe is drafted at
[`metadata/io.github.jonnyczi.copypartyclient.yml`](../metadata/io.github.jonnyczi.copypartyclient.yml).
What's left:

1. **Push the public mirror + a release tag.** F-Droid builds from the public
   GitHub repo `github.com/jonnyczi/copyparty-client`; the recipe pins
   `commit: v1.0.0`. So a `vX.Y.Z` tag (matching `app.json`) must exist there.
   See `release-pipeline.md` → Versioning (`npm run bump-version`, then tag).
2. **Validate locally before the MR.** Install `fdroidserver` and run
   `fdroid build io.github.jonnyczi.copypartyclient` against the recipe. Expo on
   F-Droid's Debian buildserver is fiddly — expect to iterate. The scanner must
   report no non-free libs and the build must produce the APK. The recipe already
   overrides `gradle.properties` to ship ARM-only, matching the GitHub/Play builds.
3. **Submit** a copy of the recipe as a merge request to the `fdroiddata` repo;
   F-Droid compiles + signs (with its own key) + publishes.

**Caveat to remember:** F-Droid signs with its own key, so an F-Droid install is
not cross-updatable with the Play/GitHub build (accepted).

**Store art is done** — `fastlane/metadata/android/en-US/images/` now holds the
512² icon and the 1024×500 feature graphic, generated by `npm run gen-brand`.
Still missing from that tree, and required by F-Droid: `title.txt`,

## Deferred: copyparty handshake 422 on partial-upload dedup collision ⚪

up2k dedups by content hash server-wide. When the only server-side copy of some
content is a **partial** upload (left behind by an interrupted run), uploading
identical content to any *other* folder fails `handshake 422` — and retries fail
identically forever. Surfaced nicely in the run UI, but there is no recovery.
Deliberately deferred from the background-sync-reliability branch (2026-07-04):
needs copyparty protocol research (a dedup-bypass/force flag on handshake, or
detect-and-resume of the partial in its original location) and possibly an
upstream issue. Repro + evidence in the 2026-07-04 verification session
(`tmp/background-sync-verification-report.md`, defect 6). The foreground-service
work makes stranded partials much rarer, so severity is reduced.

  of `/background-sync` at `/permissions`, reached from Settings → Privacy. One
  row per app-wide permission (photos, photo location, notifications) with an
  explicit required/optional level — camera-roll access is only *required* when
  a media job actually exists — and, for the optional ones, a plain statement of
  what leaving them off costs. Buttons ask in-app first and only fall back to
  system settings once Android stops prompting. A second section covers per-job
  SAF folder grants, which are not app-wide permissions and can be lost silently.

  check is now `POST_NOTIFICATIONS` **and** a new native
